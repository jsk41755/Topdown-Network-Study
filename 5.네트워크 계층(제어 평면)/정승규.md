## 5.1 개요

### 1. 제어 평면(Control Plane)의 본질

4장에서 다룬 '데이터 평면(Data Plane)'이 라우터로 들어온 패킷을 알맞은 출구로 내보내는 단순한 근육 노동(포워딩)이라면, 5장의 **'제어 평면'은 송신지부터 목적지까지의 전체 경로를 계산하여 지도를 그리는 '두뇌(라우팅)' 역할**을 담당한다.

제어 평면이 네트워크의 최적 경로를 계산하여 각 라우터의 포워딩 테이블(Forwarding Table)에 그 결과값을 채워 넣어주어야만, 비로소 데이터 평면이 패킷을 올바르게 전달할 수 있다. 이 포워딩 테이블을 어떻게 계산하고 배포할 것인가에 따라 현대 네트워크의 구조는 크게 두 가지 방식으로 나뉜다.

### 2. 제어 평면을 구현하는 두 가지 접근법

**가. 전통적 방식: 라우터별 제어 (Per-router control)**

지난 수십 년간 인터넷을 지탱해 온 전통적인 분산형 라우팅 방식이다.

- **구조:** 모든 라우터가 내부에 각자의 라우팅 알고리즘(소프트웨어)을 가지고 있다. 즉, 라우터 하나하나가 독립적인 '두뇌'를 갖춘 형태이다.
- **동작 방식:** 라우터들은 이웃 라우터들과 서로 라우팅 메시지(연결 상태, 링크 비용 등)를 끊임없이 주고받는다. 이 정보를 바탕으로 각 라우터는 자율적으로 수학적 계산을 수행해 자신만의 포워딩 테이블을 완성한다.
- **특징:** 완벽한 분산형 시스템이므로 특정 라우터가 고장 나더라도 주변 라우터들이 알아서 우회 경로를 다시 계산해 낸다. 우리가 흔히 아는 OSPF, BGP 같은 라우팅 프로토콜이 이 방식으로 동작한다.

**나. 현대적 방식: 논리적으로 집중된 제어 (Logically centralized control)**

최근 대규모 데이터센터를 중심으로 급격히 확산된 SDN(소프트웨어 정의 네트워크, Software-Defined Networking)의 핵심 원리이다.

- **구조:** 개별 라우터에서 '두뇌(라우팅 기능)'를 모두 제거하고, 이를 별도의 서버인 **'원격 컨트롤러(Remote Controller)'** 한 곳으로 통합한다. 라우터에는 지시받은 대로 패킷을 나르는 '근육(포워딩 하드웨어)'만 남는다.
- **동작 방식:** 중앙 집중형 컨트롤러가 전체 네트워크의 연결 상태를 위에서 한눈에 내려다보며 최적의 경로를 일괄적으로 계산한다. 그 후, 완성된 포워딩 테이블 규칙을 각 라우터에게 단순히 '설치(다운로드)'해 준다.
- **특징:** 관리자가 네트워크 전체의 트래픽 흐름을 소프트웨어 코딩을 통해 중앙에서 자유자재로 조작(Traffic Engineering)하기 매우 쉽다.

### 3. 전통적 제어 vs 집중된 제어 (SDN) 요약 비교

|  | **라우터별 제어 (전통적 라우터)** | **논리적으로 집중된 제어 (SDN)** |
| --- | --- | --- |
| **의사결정 주체** | 수많은 라우터들의 협력과 분산 계산 | 중앙의 단일 원격 컨트롤러 |
| **라우터의 역할** | 포워딩(데이터 평면) + 라우팅(제어 평면) | 포워딩(데이터 평면) 기능만 수행 |
| **장단점** | 단일 장애점(SPOF)이 없어 생존성이 강하나, 복잡한 경로 조작이 어려움 | 네트워크 전체 관리가 직관적이고 쉬우나, 컨트롤러 마비 시 치명적 |

## 5.2 라우팅 알고리즘

### 1. 링크 상태 (Link-State, LS) 알고리즘

네트워크 내의 **모든 라우터가 네트워크 전체의 완벽한 지도를 가지고** 최단 경로를 계산하는 방식이다. 대표적으로 **다익스트라(Dijkstra) 알고리즘**을 사용하며, 실제 프로토콜로는 OSPF가 있다.

- **정보 수집 (브로드캐스트):** 각 라우터는 자신과 직접 연결된 링크의 비용 정보(링크 상태)를 네트워크 내의 모든 라우터에게 방송(Broadcast)한다. 결과적으로 모든 라우터는 동일하고 완전한 네트워크 지도를 확보하게 된다.
- **경로 계산:** 완벽한 지도가 완성되면, 각 라우터는 다익스트라 알고리즘을 돌려 자신을 출발점으로 삼아 모든 목적지까지의 최단 경로 트리를 독립적으로 계산한다.
- **특징:**
    - **장점:** 전체 지도를 보고 계산하므로 경로 계산이 매우 빠르고 정확하며, 라우팅 루프(패킷이 뱅뱅 도는 현상)가 발생하지 않는다.
    - **단점:** 모든 라우터가 상태 정보를 브로드캐스트해야 하므로 네트워크 대역폭(메시지 오버헤드)을 많이 소모한다. 트래픽에 따라 링크 비용이 변할 경우 경로가 계속 뒤바뀌는 진동(Oscillation) 현상이 발생할 수 있다.

### 2. 거리 벡터 (Distance-Vector, DV) 알고리즘

전체 지도를 모른 채, 오직 **직접 연결된 이웃 라우터와만 정보를 교환**하며 점진적으로 최단 경로를 학습하는 방식이다. **벨만-포드(Bellman-Ford) 알고리즘**을 기반으로 하며, 실제 프로토콜로는 RIP와 BGP가 있다.

- **정보 수집 (소문 퍼뜨리기):** 각 라우터는 자신이 아는 '목적지까지의 거리 정보(거리 벡터)'를 오직 **이웃 라우터에게만** 전달한다. 이웃이 주는 정보를 듣고 내 정보를 업데이트한 뒤, 변경된 내용을 다시 이웃에게 알려주는 과정을 반복한다.
- **계산 원리 (벨만-포드 방정식):**

$$
d_x(y) = \min_v \{c(x,v) + d_v(y)\}
$$

(노드 $x$에서 $y$까지의 최소 비용은, $x$의 이웃인 $v$로 가는 비용 $c(x,v)$와 $v$에서 $y$까지 가는 최소 비용 $d_v(y)$를 합친 값 중 가장 작은 값이다.)

- **특징:**
    - **장점:** 이웃과만 통신하므로 초기 메시지 오버헤드가 적다.
    - **단점:** 소문(간접 정보)에 의존하므로 최적 경로를 찾아 수렴하는 데 시간이 오래 걸린다. 특히 네트워크 어딘가 끊어졌을 때, 잘못된 정보를 서로 주고받으며 비용이 무한대로 치솟는 **'무한 계수(Count-to-Infinity)'** 문제(라우팅 루프)가 발생할 수 있다.

**💡 요약 비교 테이블**

| **비교 항목** | **링크 상태 (LS, 다익스트라)** | **거리 벡터 (DV, 벨만-포드)** |
| --- | --- | --- |
| **네트워크 지식** | 전체 네트워크 토폴로지 (완벽한 지도) | 이웃 라우터와의 링크 비용 (국지적 정보) |
| **정보 교환 범위** | 네트워크 내 모든 라우터 (브로드캐스트) | 오직 직접 연결된 이웃 라우터 |
| **수렴 속도** | 빠름$(O|N|^2)$ 등 계산 후 즉각 적용) | 느림 (이웃의 이웃을 거쳐야 함) |
| **견고성(오류 시)** | 계산 오류가 해당 라우터에만 국한됨 | 오류 정보가 네트워크 전체로 전파될 수 있음 |

## 5.3 인터넷에서의 AS 내부 라우팅: OSPF

### 1. 자율 시스템(AS, Autonomous System)의 등장 배경

인터넷에는 수십억 대의 라우터가 있다. 이 모든 라우터가 서로 링크 상태 정보를 브로드캐스트하며 다익스트라 알고리즘을 돌린다면, 라우터의 메모리는 터져버리고 네트워크는 라우팅 정보만 주고받다가 마비될 것이다.

그래서 인터넷은 전 세계의 라우터들을 '자율 시스템(AS)'이라는 수많은 덩어리로 쪼갰다. 하나의 AS는 동일한 기관(예: SKT, KT, 구글, 대학 네트워크 등)의 관리하에 있는 라우터들의 집합이다.

- **AS 내부 라우팅 (IGP):** 우리 동네(AS) 안에서 목적지를 찾는 방법. (여기에 OSPF가 쓰인다.)
- **AS 간 라우팅 (BGP):** 우리 동네에서 다른 동네(다른 AS)로 넘어가는 방법.

### 2. OSPF의 핵심 특징

OSPF는 이름(Open Shortest Path First)에 나와 있듯, 특정 기업의 독점 기술이 아니라 누구나 쓸 수 있는 '공개된(Open)' 프로토콜이며, 최단 경로(Shortest Path)를 다익스트라 알고리즘으로 찾아내는 방식이다.

- **보안 (Authentication):** 모든 OSPF 메시지는 인증 과정을 거친다. 해커가 가짜 라우터를 연결해 엉터리 라우팅 정보를 퍼뜨리는 것을 원천 차단한다.
- **동일 비용 다중 경로 (ECMP):** 목적지까지 가는 비용이 같은 경로가 2개 이상 있다면, 트래픽을 한쪽으로 몰지 않고 여러 경로로 분산시켜 전송(로드 밸런싱)할 수 있다.
- **멀티캐스트 활용:** 대역폭 낭비를 막기 위해 전체 브로드캐스트를 하지 않고, OSPF를 사용하는 라우터들끼리만 약속된 멀티캐스트 주소(`224.0.0.5`, `224.0.0.6`)로 소통한다.

### 3. 계층적 OSPF: 확장성 문제의 해결책

AS 하나만 해도 내부 라우터가 수백, 수천 개가 될 수 있다. 아무리 AS로 쪼갰다 하더라도 수천 대가 동시에 링크 상태 정보를 브로드캐스트하면 무리가 간다.
그래서 OSPF는 AS 내부를 다시 '구역(Area)'이라는 계층 구조로 한 번 더 쪼갠다.

| **라우터/구역 종류** | **역할** |
| --- | --- |
| **백본 구역 (Area 0)** | OSPF 도메인의 중심 교차로. 모든 다른 지역 구역은 반드시 Area 0과 연결되어야 한다. |
| **지역 구역 (Local Area)** | 일반 라우터들이 모여 있는 곳. 링크 상태 정보(LSA)는 오직 이 구역 내부에서만 브로드캐스트된다. |
| **구역 경계 라우터 (ABR)** | 지역 구역과 백본 구역에 양다리를 걸치고 있는 라우터. 자기 구역의 경로 정보를 요약해서 백본으로 넘겨준다. |

### 4. OSPF 라우터의 동작 과정

**1.이웃 발견 (Hello 패킷):**멀티캐스트 활용.
라우터가 켜지면 인접한 라우터들에게 Hello 패킷을 주기적으로 보내 서로의 존재를 확인하고 이웃(Neighbor) 관계를 맺는다.

**2.데이터베이스 동기화 (Database Exchange):**
서로가 가지고 있는 링크 상태 데이터베이스(LSDB)의 요약본을 교환하여, 자신에게 없는 정보가 무엇인지 파악한다.

**3.링크 상태 업데이트 (LSA Flooding):**
부족한 정보(전체 네트워크의 링크 비용, 연결 상태 등)를 요청하고 받아 데이터베이스를 완벽하게 일치시킨다. 네트워크에 변화가 생겼을 때도 이 과정을 거친다.

**4.최단 경로 계산 (Dijkstra):**
완성된 데이터베이스를 바탕으로 다익스트라 알고리즘을 실행하여, 모든 목적지까지의 최단 경로 트리를 계산하고 포워딩 테이블에 기록한다.

요약하자면, OSPF는 **'링크 상태 알고리즘'이라는 수학적 모델을, 'Area 분할'이라는 공학적 최적화를 통해 현실의 대규모 네트워크에 성공적으로 적용한 사례**라고 볼 수 있다.

## 5.4 인터넷 서비스 제공업자(ISP) 간의 라우팅: BGP

이전 절(5.3절)에서 배운 OSPF가 하나의 자율 시스템(AS, 예를 들어 SKT 네트워크) '내부'에서 길을 찾는 방법이라면, BGP(Border Gateway Protocol)는 전 세계의 수많은 AS들을 서로 연결하여 오늘날의 거대한 '인터넷'을 완성하는 **접착제** 역할을 한다. 인터넷에서 통용되는 유일한 외부 게이트웨이 라우팅 프로토콜이 바로 BGP이다.

### 1. BGP의 핵심 철학: 성능보다 '정책과 돈'

내부 라우팅(OSPF)은 오직 '가장 빠른 길(최소 비용)'을 찾는 데 집중한다. 하지만 서로 다른 회사(ISP) 간에 트래픽을 주고받는 BGP는 다르게 작동한다.

BGP에서 최적 경로를 결정하는 1순위는 물리적인 속도가 아니라 '비즈니스 정책(Policy)'이다. 아무리 빠르고 짧은 경로라도, 경쟁사 네트워크를 거쳐야 하거나 데이터 통행료(Transit)를 비싸게 내야 한다면 그 길로 가지 않는다. 즉, BGP는 "가장 빠르진 않더라도, 돈이 덜 들고 우리 회사의 정책에 부합하는 길"을 찾는 프로토콜이다.

### 2. BGP의 두 가지 형태 (eBGP vs iBGP)

BGP는 AS 간에 정보를 주고받는 외부 역할과, 그 정보를 AS 내부 라우터들에게 퍼뜨리는 내부 역할을 모두 수행해야 한다.

| **구분** | **목적** | **연결 대상** |
| --- | --- | --- |
| **eBGP** (External BGP) | **다른 동네(AS)의 정보 얻기** | 서로 다른 AS의 경계 라우터끼리 연결 |
| **iBGP** (Internal BGP) | **얻어온 정보를 우리 동네에 퍼뜨리기** | 같은 AS 내부에 있는 모든 라우터끼리 연결 |

경계 라우터는 eBGP를 통해 외부 ISP로부터 "X라는 목적지로 가려면 우리를 거치면 돼!"라는 정보를 얻고, 이를 iBGP를 통해 자기 AS 내부의 모든 라우터에게 방송하여 전체 네트워크가 길을 알게 만든다.

### 3. 경로 벡터 (Path Vector)와 주요 속성

BGP는 목적지에 대한 정보(서브넷 프리픽스)를 교환할 때, 그 경로가 거쳐온 모든 AS의 목록 등 다양한 '속성(Attribute)'을 함께 묶어서 전달한다. 이를 **경로 벡터 알고리즘**이라고 한다.

- **AS-PATH:** 목적지까지 가기 위해 거쳐야 하는 AS 번호들의 목록 (예: `AS100 -> AS200 -> AS300`). 이 목록에 이미 자신의 AS 번호가 들어있다면, 패킷이 뱅뱅 돌고 있다는 뜻이므로 해당 경로를 즉시 버려 **라우팅 루프를 방지**한다.
- **NEXT-HOP:** 그 경로를 타기 위해 AS 밖으로 패킷을 던져야 할(포워딩해야 할) 다음 라우터의 IP 주소.

### 4. BGP 경로 선택 프로세스

BGP 라우터는 특정 목적지로 가는 경로를 여러 개 받았을 때, 다음 순서대로 필터를 거치며 최종적으로 딱 하나의 경로만 선택한다.

**1. 지역 선호도 (Local Preference) 속성:**가장 중요한 기준 (관리자 설정).
네트워크 관리자가 설정한 비즈니스 정책 값이 가장 높은 경로를 무조건 최우선으로 선택한다. (예: 비용이 저렴한 경로에 높은 점수 부여)

**2. 최단 AS-PATH:**
지역 선호도가 같다면, 거쳐 가야 할 AS의 개수(AS-PATH의 길이)가 가장 적은 경로를 선택한다.

**3. 다중 출구 식별자 (MED):**
AS-PATH까지 같다면, 이웃 AS가 자신에게 넘겨준 MED(Multi-Exit Discriminator) 값을 비교하여, 이웃이 선호하는 경로로 트래픽을 내보낸다.

**4. eBGP 우선:**
eBGP를 통해 직접 배운 경로가 iBGP를 통해 건너건너 배운 경로보다 우선한다.

**5. 뜨거운 감자 라우팅 (Hot Potato Routing):**
여기까지 조건이 모두 같다면, 목적지 AS로 가는 여러 출구 중 **내부 라우팅(OSPF) 비용이 가장 적은 출구**를 선택한다. 즉, 우리 동네(AS) 안에서 트래픽을 오래 붙잡지 않고 최대한 빨리 다른 AS로 던져버리는(뜨거운 감자 넘기듯) 방식이다.

## 5.5 소프트웨어 정의 네트워크(SDN) 제어 평면

5.1절에서 언급했듯, 과거의 라우터는 스스로 경로를 계산하는 '두뇌(제어 평면)'와 패킷을 전달하는 '근육(데이터 평면)'이 하나의 기계 안에 결합되어 있었다. OSPF나 BGP 같은 프로토콜이 바로 이 분산된 두뇌들이 서로 대화하는 방식이다.

하지만 SDN(Software-Defined Networking)은 이 두뇌를 수많은 라우터(스위치)에서 전부 적출하여, 중앙의 똑똑한 서버 하나로 통합하는 혁명적인 패러다임이다.

### 1. SDN 아키텍처의 3대 계층

SDN은 크게 세 가지 계층으로 나뉘며, 각 계층 사이에는 표준화된 API(인터페이스)가 존재한다.

| **계층 (Layer)** | **역할** | **비유** |
| --- | --- | --- |
| **네트워크 제어 애플리케이션** | "특정 트래픽은 차단해라", "경로를 이쪽으로 우회해라" 등 관리자의 비즈니스 로직과 의도를 정의하는 소프트웨어 프로그램들. | 사장님 (지시 내림) |
| **SDN 컨트롤러 (제어 평면)** | 네트워크의 운영체제(OS). 전체 네트워크의 상태(토폴로지)를 유지하고, 위에서 내려온 지시를 장비가 알아들을 수 있는 규칙으로 번역해 배포한다. | 중간 관리자 (번역 및 배포) |
| **데이터 평면 (네트워크 장비)** | 컨트롤러가 내려준 '매치-액션(Match-Action) 규칙'에 따라 들어오는 패킷을 전달하거나 버리는 단순 하드웨어 스위치. | 현장 실무자 (단순 반복) |

### 2. 컨트롤러를 관통하는 두 개의 인터페이스 (API)

SDN의 핵심은 컨트롤러가 위아래와 어떻게 소통하느냐에 있다.

- **노스바운드(Northbound) API:** 컨트롤러와 그 위의 애플리케이션 계층 사이의 통신 규격이다. 주로 개발자 친화적인 REST API를 사용한다. 네트워크 애플리케이션 개발자는 물리적인 라우터가 어떻게 생겼는지 알 필요 없이, 이 API를 호출해 "보안 정책 적용해 줘"라고 명령만 내리면 된다.
- **사우스바운드(Southbound) API:** 컨트롤러와 그 아래의 물리적 스위치들 사이의 통신 규격이다. 컨트롤러가 계산한 포워딩 테이블(흐름 테이블)을 스위치에 다운로드할 때 사용한다. 가장 대표적인 사우스바운드 프로토콜이 바로 OpenFlow(오픈플로우)이다.

### 3. 왜 SDN을 사용하는가? (SDN의 장점)

과거의 OSPF나 BGP로도 네트워크는 잘 돌아갔다. 그런데 왜 구글, 아마존 같은 거대 IT 기업들은 데이터센터 네트워크를 전부 SDN으로 바꿨을까?

1. **트래픽 엔지니어링의 유연성:** 기존 라우팅 방식에서는 트래픽 흐름을 인위적으로 바꾸려면 링크 가중치를 조작해야 하는 등 꼼수가 필요했다. SDN은 중앙에서 전체 지도를 보고 있으므로, 특정 트래픽만 우회시키거나 다중 경로로 분산시키는 작업을 코드 몇 줄로 완벽하게 통제할 수 있다.
2. **하드웨어 종속성 탈피:** 라우팅 로직이 소프트웨어(컨트롤러)로 빠졌기 때문에, 밑단의 스위치는 값비싼 시스코(Cisco) 장비 대신 규칙만 단순 실행하는 저렴한 '화이트박스(White-box) 스위치'를 대량으로 사다 쓸 수 있게 되었다.
3. **네트워크의 프로그래밍화:** 새로운 라우팅 프로토콜을 전 세계 라우터에 적용하려면 십수 년이 걸리지만, SDN에서는 컨트롤러의 소프트웨어만 업데이트하면 네트워크 전체의 동작 방식을 즉시 바꿀 수 있다.

결론적으로 SDN은 하드웨어에 묶여 있던 네트워크를 '소프트웨어 개발의 영역'으로 해방시킨 기술이다.

## 5.6 인터넷 제어 메시지 프로토콜(ICMP)

IP(인터넷 프로토콜)는 데이터를 목적지까지 전달하는 데만 집중하는 '최선형(Best-Effort)' 서비스다. 가다가 패킷이 버려지거나 경로를 찾지 못해도 IP 스스로는 송신자에게 오류를 알려줄 방법이 없다. 이 약점을 보완하기 위해 IP와 찰떡처럼 붙어 다니며 **네트워크의 오류를 보고하고 상태를 진단하는 역할**을 하는 것이 바로 ICMP(Internet Control Message Protocol)이다.

ICMP 메시지는 독립적으로 날아가지 않고, 일반 데이터처럼 **IP 데이터그램의 페이로드(데이터 부분)에 담겨서** 전송된다. (IP 헤더의 프로토콜 번호 1번이 ICMP를 의미한다.)

### 1. ICMP 메시지의 구조와 주요 타입

ICMP 메시지는 문제가 발생한 원인을 정확히 짚어주기 위해 타입(Type)과 코드(Code)라는 두 가지 핵심 필드를 사용한다. 여기에 오류를 발생시킨 원본 IP 패킷의 헤더와 첫 8바이트 데이터를 덧붙여서 송신자에게 돌려보낸다. (송신자가 "아, 내가 보낸 이 패킷 때문에 에러가 났구나" 하고 알 수 있게 하기 위함이다.)

| **타입** | **코드** | **의미** | **설명** |
| --- | --- | --- | --- |
| **0** | 0 | Echo Reply (에코 응답) | Ping 요청에 대한 정상 응답 |
| **8** | 0 | Echo Request (에코 요청) | Ping을 보낼 때 사용하는 요청 |
| **3** | 0 | 목적지 네트워크 도달 불가 | 라우터가 목적지 네트워크로 가는 경로를 모름 |
| **3** | 1 | 목적지 호스트 도달 불가 | 네트워크엔 도착했는데 해당 컴퓨터(호스트)가 꺼져 있음 |
| **3** | 3 | 목적지 포트 도달 불가 | 컴퓨터엔 도착했는데 해당 포트(앱)가 닫혀 있음 |
| **11** | 0 | TTL(Time-To-Live) 초과 | 패킷이 네트워크 루프에 빠져 수명이 다해 버려짐 |

### 2. ICMP를 활용한 대표적인 네트워크 진단 도구

우리가 일상적으로 네트워크가 끊겼을 때 가장 먼저 입력해 보는 명령어들이 바로 이 ICMP를 교묘하게 활용한 프로그램들이다.

#### ① Ping (연결 상태 확인)

출발지 컴퓨터가 목적지로 **ICMP Type 8 (Echo Request)** 패킷을 보낸다. 목적지 컴퓨터가 살아있고 네트워크가 연결되어 있다면, **ICMP Type 0 (Echo Reply)** 패킷을 만들어 돌려보낸다. 이를 통해 왕복 시간(RTT)과 패킷 손실률을 측정한다.

#### ② Traceroute (경로 추적)

목적지까지 가는 데 어떤 라우터들을 거치는지 추적하는 도구다. 이 프로그램은 IP 패킷의 **TTL(수명)** 필드와 **ICMP Type 11 (시간 초과)** 에러 메시지를 기발하게 응용한다.

**Traceroute의 동작 원리:**
**1.TTL=1 패킷 전송:**
출발지는 수명이 1인 패킷을 보낸다. 첫 번째 라우터에 도착하면 라우터는 TTL을 0으로 깎고, 수명이 다했으므로 패킷을 버린다. 그리고 출발지에게 **ICMP Type 11 (시간 초과)** 메시지를 보낸다. 출발지는 이 메시지의 발신자 IP를 보고 "첫 번째 라우터는 여기구나" 하고 기록한다.

**2.TTL=2 패킷 전송:**
이번엔 수명이 2인 패킷을 보낸다. 첫 번째 라우터를 통과(TTL=1)하고 두 번째 라우터에 도착하면 TTL이 0이 되어 패킷이 버려진다. 두 번째 라우터가 **ICMP Type 11**을 보낸다. 출발지는 두 번째 라우터의 주소를 알아낸다.

**3.과정 반복:**
이런 식으로 TTL을 3, 4, 5... 씩 계속 늘려가며 보낸다. 매번 다음 순서의 라우터가 에러 메시지를 뱉어내며 자신의 존재를 노출하게 된다.

**4.목적지 도착 (Port Unreachable):**
패킷이 마침내 진짜 목적지 컴퓨터에 도착한다. Traceroute는 일부러 존재하지 않는 엉뚱한 포트 번호(예: UDP 33434)로 패킷을 보낸다. 목적지 컴퓨터는 포트가 닫혀 있으므로 **ICMP Type 3 Code 3 (포트 도달 불가)** 메시지를 반환한다. 출발지는 이 메시지를 받는 순간 추적이 끝났음을 알고 프로그램을 종료한다.

## 5.7 네트워크 관리와 SNMP, NETCONF/YANG

수천 대의 라우터, 스위치, 방화벽이 얽혀 있는 거대한 네트워크를 사람의 손으로 일일이 관리하는 것은 불가능하다. 따라서 중앙의 관리 서버(Managing Server)와 각 네트워크 장비에 설치된 에이전트(Agent)가 서로 통신하며 상태를 감시하고 설정을 변경하는 '자동화된 통제 시스템'이 필요한데, 이것이 바로 네트워크 관리의 핵심이다.

이 분야는 크게 과거부터 쓰이던 전통적인 방식(SNMP)과 SDN(소프트웨어 정의 네트워크) 시대에 맞춰 등장한 현대적인 방식(NETCONF/YANG)으로 나뉜다.

### 1. 전통적인 방식: SNMP와 MIB

과거 네트워크 관리의 사실상 표준이었으며 현재까지도 널리 쓰이는 프로토콜이 SNMP(Simple Network Management Protocol)이다.

- **MIB (Management Information Base):** 각 네트워크 장비가 스스로의 상태(예: CPU 사용량, 포트 활성화 여부, 처리한 패킷 수)를 기록해 두는 일종의 가상 데이터베이스다.
- **SNMP의 두 가지 통신 방식:**
    1. **요청/응답 (Request/Response):** 매니저가 주기적으로 장비에게 "지금 1번 포트 트래픽 양이 얼마야?"라고 물어보면(`GetRequest`), 에이전트가 MIB에서 값을 읽어 대답한다.
    2. **트랩 (Trap):** 장비에 온도가 급상승하거나 포트가 다운되는 등 심각한 오류가 발생했을 때, 매니저가 묻기도 전에 에이전트가 스스로 경고 메시지를 쏘는 능동적인 방식이다.

SNMP는 장비의 상태를 '읽고(모니터링)' 문제를 파악하는 데는 아주 훌륭했지만, 수백 대의 장비에 복잡한 설정을 '쓰기(Configuration)'에는 기능이 턱없이 부족했다.

### 2. 현대적인 방식: NETCONF와 YANG

클라우드와 SDN 시대가 열리면서 장비 설정을 소프트웨어 코드로 정교하게 통제할 필요성이 커졌다. 제조사(Cisco, Juniper 등)마다 제각각이던 명령어(CLI)를 통일하고 자동화하기 위해 등장한 콤비가 바로 **NETCONF**와 **YANG**이다.

- **YANG (데이터 모델링 언어):** 네트워크 장비의 설정 데이터가 어떻게 생겨야 하는지 그 '구조와 제약 조건'을 정의하는 엄격한 언어다. 프로그래밍에서 클래스나 구조체를 선언하는 것과 같다.
- **NETCONF (통신 프로토콜):** YANG으로 정의된 규격에 맞춰, 실제 설정값(보통 XML 또는 JSON 형태)을 장비에 전달하는 프로토콜이다.

### 3. 핵심 비교 요약

가장 중요한 차이점은 데이터 전송의 신뢰성과 **트랜잭션(Transaction) 지원 여부**다. NETCONF는 여러 장비를 동시에 설정하다가 중간에 하나라도 실패하면, 전체 설정을 이전 상태로 되돌리는 롤백(Rollback)이 가능해 설정 꼬임을 방지할 수 있다.

| **비교 항목** | **SNMP** | **NETCONF / YANG** |
| --- | --- | --- |
| **주 목적** | 네트워크 상태 감시 및 모니터링 | 대규모 네트워크 구성(Configuration) 통제 |
| **데이터 구조** | MIB (단순 계층형 변수) | YANG (복잡한 트리 구조 및 제약조건) |
| **메시지 형태** | 단순 바이트 (BER 인코딩) | XML 또는 JSON |
| **전송 계층** | UDP (빠르지만 신뢰성 낮음) | TCP / SSH (보안 및 신뢰성 보장) |
| **트랜잭션 지원** | 불가능 | 가능 (실패 시 롤백 지원) |

결론적으로, **SNMP**가 장비가 잘 살아있는지 확인하는 '청진기'라면, **NETCONF와 YANG**은 수많은 장비의 설정을 일관된 코드로 통제하는 '설계도이자 수술칼'이라고 이해하면 된다.
