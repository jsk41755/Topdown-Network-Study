# 네트워크 보안 8장 — 급식도 이해하는 쉬운 설명

> 네트워크 보안의 핵심은 **누가 보냈는지 확인하고, 내용을 숨기고, 중간에 바뀌지 않았는지 검사하는 것**이다.

## 먼저 보는 핵심 도구

| 도구 | 급식실 비유 | 해결하는 문제 |
|---|---|---|
| 암호화 | 자물쇠 달린 급식 상자 | 남이 내용을 보지 못하게 함 |
| 해시 | 음식의 고유한 지문 | 내용이 바뀌었는지 확인 |
| MAC | 둘만 가진 비밀 도장 | 무결성 + 공유키 소유자 확인 |
| 전자서명 | 나만 찍을 수 있는 개인 도장 | 송신자 인증 + 무결성 |
| 인증서 | 학교가 발급한 학생증 | 공개키 주인이 누구인지 보증 |

---

# 8.1 네트워크 보안이란 무엇인가?

네트워크 보안은 누군가 통신을 **엿보거나, 고치거나, 사칭하는 행위**를 어떻게 막을지 다루는 분야다.

## 안전한 통신의 네 가지 조건

- **기밀성**: 지정된 사람만 내용을 읽을 수 있어야 한다.
- **무결성**: 전달 중 내용이 바뀌지 않아야 한다.
- **종단점 인증**: 지금 대화하는 상대가 진짜 그 사람인지 확인해야 한다.
- **운영 보안**: 방화벽·IDS 등을 이용해 조직 전체를 보호해야 한다.

앨리스가 밥에게 `오늘 급식실 창고 비밀번호는 1234`라고 보낼 때 침입자 이브는 다음 행동을 할 수 있다.

- 몰래 읽기: **도청**
- `1234`를 `9999`로 변경: **변조**
- 앨리스인 척 가짜 메시지 보내기: **위조**
- 메시지를 저장했다가 다시 보내기: **재생 공격**
- 메시지를 중간에서 없애기: **삭제**

따라서 암호화 하나만으로 모든 보안 문제가 해결되지는 않는다.

---

# 8.2 암호의 원리

암호화 전 메시지를 **평문**, 암호화된 결과를 **암호문**이라고 한다.

```text
평문 + 암호화 알고리즘 + 키 → 암호문
암호문 + 복호화 알고리즘 + 키 → 평문
```

암호 알고리즘은 공개되어도 괜찮다. 비밀이어야 하는 것은 알고리즘이 아니라 **키**다. 자물쇠의 구조는 공개되어도 실제 열쇠만 안전하게 보관하면 되는 것과 같다.

## 대칭키 암호화

암호화와 복호화에 사실상 같은 비밀키를 사용한다.

```text
앨리스 ← 같은 비밀키 → 밥
```

- 장점: 계산이 빠르다.
- 단점: 두 사람이 비밀키를 안전하게 공유하기 어렵다.
- 대표적인 현대 알고리즘: **AES**

## 공개키 암호화

한 사람이 서로 연결된 두 개의 키를 가진다.

- **공개키**: 누구에게나 공개할 수 있다.
- **개인키**: 소유자만 보관한다.

밥에게 비밀 메시지를 보내려면 밥의 공개키로 암호화한다. 그러면 밥의 개인키로만 복호화할 수 있다.

- 장점: 비밀키를 미리 공유하지 않아도 된다.
- 단점: 대칭키보다 계산이 느리다.

## 고전 암호

### 카이사르 암호

알파벳을 일정한 칸만큼 미는 방법이다.

```text
A → D
B → E
C → F
```

가능한 이동 칸이 적어서 전부 시험해 보면 금방 풀린다.

### 단일 문자 대응 암호

각 알파벳을 임의의 다른 알파벳에 대응시킨다. 경우의 수는 많지만 영어에서 `e`, `t`처럼 자주 등장하는 글자의 빈도를 분석하면 대응 관계를 추측할 수 있다.

### 다중 문자 대응 암호

같은 글자도 위치에 따라 다른 규칙으로 암호화한다.

```text
첫 번째 A → K
두 번째 A → Q
세 번째 A → K
```

단순한 빈도 분석을 어렵게 만들지만 현대적인 보안에는 여전히 부족하다.

## 공격자의 정보 수준

- **암호문 단독 공격**: 암호문만 가지고 분석한다.
- **알려진 평문 공격**: 평문 일부와 그에 대응하는 암호문을 알고 있다.
- **선택 평문 공격**: 공격자가 원하는 평문을 암호화시켜 결과를 관찰할 수 있다.

안전한 암호 시스템은 알고리즘이 공개되고 공격자가 일부 평문을 선택할 수 있다고 가정해도 안전해야 한다.

## 블록 암호화

AES 같은 블록 암호는 데이터를 고정 크기 블록으로 잘라 처리한다.

```text
긴 메시지
→ [블록 1][블록 2][블록 3]
→ 각각 암호화
```

AES는 거대한 변환표를 저장하는 대신, 키를 이용한 여러 라운드의 계산으로 복잡한 변환을 만든다. 입력 비트 하나의 변화가 출력 전체에 퍼지도록 여러 번 섞는다.

DES와 3DES는 역사적으로 중요하지만 현재 새 시스템에 사용할 암호는 아니다. 실무에서는 AES가 대표적이다.

## CBC: 암호 블록 체이닝

각 블록을 독립적으로 암호화하면 같은 평문 블록에서 같은 암호문이 나온다. 공격자가 반복 패턴을 발견할 수 있다.

CBC는 이전 암호문과 현재 평문을 XOR한 뒤 암호화한다.

```text
c₀ = IV
cᵢ = Eₖ(mᵢ XOR cᵢ₋₁)
mᵢ = Dₖ(cᵢ) XOR cᵢ₋₁
```

첫 블록 앞에는 **초기화 벡터 IV**를 사용한다.

> CBC는 암호화만 제공할 뿐 그 자체로 변조를 막지는 못한다. 현재는 암호화와 무결성을 함께 제공하는 AES-GCM이나 ChaCha20-Poly1305 같은 AEAD 방식이 주로 사용된다.

## RSA

RSA는 큰 수의 소인수분해가 어렵다는 성질을 이용한 공개키 암호 방식이다.

```text
공개키: (n, e)
개인키: (n, d)

암호화: c = mᵉ mod n
복호화: m = cᵈ mod n
```

원문의 예를 바로잡으면 다음과 같다.

```text
p = 5, q = 7
n = 35
φ(n) = (5-1)(7-1) = 24
e = 5
d = 29  // 5×29 mod 24 = 1

m = 12
c = 12⁵ mod 35 = 17
m = 17²⁹ mod 35 = 12
```

원문 마지막의 `mod 68`은 `mod 35`가 맞다.

실제 RSA는 위 수식만 그대로 사용하는 이른바 raw RSA가 아니다. 암호화에는 OAEP, 서명에는 PSS 같은 안전한 형식을 결합한다. 자세한 내용은 [RSA PKCS #1 표준](https://www.rfc-editor.org/info/rfc8017/)에서 확인할 수 있다.

## 세션키와 하이브리드 암호화

RSA는 느리고 AES는 빠르다. 그래서 둘의 장점을 합친다.

```text
1. 임시 대칭키 Ks 생성
2. 실제 데이터는 Ks와 AES로 암호화
3. Ks만 수신자의 공개키로 암호화
4. 수신자는 개인키로 Ks를 복구
5. Ks로 실제 데이터를 복호화
```

이 임시 대칭키를 **세션키**라고 한다.

> 공개키 암호는 열쇠를 전달하고, 대칭키 암호는 실제 짐을 운반한다.

# 8.3 메시지 무결성과 전자서명

## 암호화 해시 함수

해시 함수는 길이가 제각각인 메시지를 고정 길이의 값으로 바꾼다.

```text
H("돈가스 1개") → 7A31...
H("돈가스 2개") → 9C82...
```

글자 하나만 바뀌어도 해시값은 크게 달라진다.

암호학적 해시 함수에는 다음 성질이 요구된다.

- 해시값에서 원문을 알아내기 어려워야 한다.
- 주어진 메시지와 같은 해시값을 가진 다른 메시지를 찾기 어려워야 한다.
- 같은 해시값을 가진 서로 다른 두 메시지를 찾기 어려워야 한다.

출력 길이가 고정되어 있으므로 충돌 자체는 반드시 존재한다. 중요한 것은 충돌을 현실적인 시간 안에 찾을 수 없어야 한다는 점이다.

> MD5와 SHA-1은 보안 목적의 새 시스템에 사용하면 안 된다. 현재는 SHA-256 같은 SHA-2 또는 SHA-3 계열을 사용한다. 참고: [NIST 해시 함수 정책](https://csrc.nist.gov/Projects/hash-functions/nist-policy-on-hash-functions)

## 해시만 보내면 왜 부족할까?

송신자가 다음을 보냈다고 해보자.

```text
(m, H(m))
```

공격자는 메시지를 `m'`으로 바꾸고 자신이 직접 `H(m')`도 계산할 수 있다.

```text
(m', H(m'))
```

수신자가 다시 해시해도 값이 일치한다. 일반 해시는 우연한 오류는 찾을 수 있지만 악의적인 위조자는 막지 못한다.

## MAC

MAC은 송신자와 수신자만 아는 비밀키를 계산에 포함한다.

```text
tag = HMAC(비밀키, 메시지)
전송: (메시지, tag)
```

공격자는 비밀키를 모르기 때문에 메시지를 바꾼 뒤 올바른 태그를 만들 수 없다.

MAC이 제공하는 것:

- 메시지 무결성
- 공유 비밀키를 아는 사람이 보냈다는 인증

단, 송신자와 수신자 모두 같은 키를 가지고 있으므로 제3자에게 둘 중 정확히 누가 만들었는지 증명하기 어렵다.

## 전자서명

전자서명은 다음 구조다.

```text
h = H(m)
서명 = Sign(송신자 개인키, h)
전송 = (m, 서명)
```

수신자는 송신자의 공개키로 서명을 검증하고 자신이 계산한 `H(m)`과 비교한다.

확인할 수 있는 것:

- 송신자의 개인키로 만든 서명인가?
- 서명 이후 메시지가 변경되지 않았는가?

전자서명을 `개인키로 암호화한다`고 설명하기도 하지만, 실제로는 암호화와 서명이 서로 다른 목적과 형식을 가진다고 이해하는 편이 정확하다.

## MAC과 전자서명의 차이

| 구분 | MAC | 전자서명 |
|---|---|---|
| 키 | 하나의 공유 비밀키 | 개인키 + 공개키 |
| 검증 가능자 | 공유키를 가진 사람 | 공개키를 가진 누구나 |
| 속도 | 비교적 빠름 | 비교적 느림 |
| 제3자에게 증명 | 어려움 | 가능 |
| 공개키 인증서 | 불필요 | 일반적으로 필요 |

## CA와 인증서

공격자가 자신의 공개키를 앨리스의 것이라고 속일 수 있다. 따라서 인증기관인 **CA**가 공개키와 신원의 연결을 확인하고 서명한다.

```text
이름: alice.example.com
공개키: PK_A
발급자: 신뢰하는 CA
CA의 전자서명
```

이것이 **인증서**다. 인증서 안에 개인키가 들어가는 것은 아니다.

# 8.4 종단점 인증

종단점 인증은 상대가 진짜 누구인지 확인하는 과정이다.

## IP 주소만 확인하는 경우

공격자는 출발지 IP 주소를 위조할 수 있다. 이를 **IP 스푸핑**이라고 한다. IP 주소는 위치 정보에 가깝지 사람의 신분증이 아니다.

## 평문 비밀번호를 보내는 경우

비밀번호를 그대로 보내면 도청자가 한 번 훔친 뒤 계속 사용할 수 있다.

## 암호화된 비밀번호를 보내는 경우

공격자가 암호문을 저장했다가 그대로 다시 보내면 인증될 수 있다. 이것이 **재생 공격**이다.

## 넌스를 이용한 Challenge–Response

넌스는 한 번만 사용하는 임의의 값이다.

```text
1. 밥: 이번 문제는 R=837291이야.
2. 앨리스: MAC(K, R)을 계산해 답한다.
3. 밥: 자신이 계산한 값과 비교한다.
```

다음 로그인에서는 새로운 넌스를 사용하므로 예전 응답을 녹화해서 재생해도 통하지 않는다.

> 넌스는 비밀일 필요가 없다. 중요한 것은 매 인증마다 새로워야 한다는 점이다.

# 8.5 전자메일 보안

보안 이메일은 기밀성, 무결성, 송신자 인증을 조립해서 만든다.

## 기밀성

정확한 순서는 다음과 같다.

```text
1. 송신자가 세션키 Ks 생성
2. C_data = Ks로 메시지 암호화
3. C_key = 수신자의 공개키로 Ks 암호화
4. (C_data, C_key) 전송
5. 수신자가 자신의 개인키로 C_key 복호화 → Ks
6. Ks로 C_data 복호화 → 원문
```

> 원문에는 키와 암호문 번호가 뒤바뀌어 있다. 세션키는 **수신자의 공개키**로 암호화해야 하며, 수신자는 먼저 암호화된 세션키를 자신의 개인키로 복호화해야 한다.

## 인증과 무결성

송신자는 메시지의 해시에 전자서명한다.

```text
서명 = Sign(송신자 개인키, H(m))
전송 = (m, 서명)
```

수신자는 송신자의 공개키로 검증한다.

## 모든 기능 통합

```text
메시지 작성
→ 메시지 해시에 서명
→ 메시지와 서명을 세션키로 암호화
→ 세션키를 수신자의 공개키로 보호
→ 전송
```

이를 흔히 **서명한 뒤 암호화한다**고 표현한다.

## PGP

PGP는 이 구조를 이메일에 적용한 것이다.

- 전자서명만 할 수 있다.
- 암호화만 할 수 있다.
- 서명과 암호화를 모두 할 수 있다.

PGP는 전통적인 CA 계층 대신 사용자들이 서로의 공개키에 서명하는 **신뢰의 그물(Web of Trust)** 모델도 사용한다.

# 8.6 TCP 연결 보안: TLS

TLS는 애플리케이션 데이터를 안전하게 전송하기 위한 프로토콜이다. **HTTPS는 HTTP를 TLS로 보호한 것**이다.

TLS가 제공하는 기능:

- 서버 인증
- 선택적인 클라이언트 인증
- 기밀성
- 데이터 무결성
- 재생·순서 변경·변조 방지

## TLS 핸드셰이크

현재 TLS 1.3을 단순화하면 다음과 같다.

```text
클라이언트                         서버
    ── 지원 알고리즘, 키 재료 ─────→
    ←──── 서버 키 재료, 인증서 ─────
    ←──── 인증서 개인키 소유 증명 ──
    ── 핸드셰이크 확인값 ──────────→
             공통 세션키 완성
```

핵심 과정:

1. 사용할 알고리즘을 합의한다.
2. 서버 인증서와 서명을 검증한다.
3. 주로 임시 Diffie–Hellman 키 교환으로 공유 비밀을 만든다.
4. 공유 비밀과 핸드셰이크 내용을 이용해 여러 트래픽 키를 유도한다.
5. 이후 애플리케이션 데이터를 대칭키로 보호한다.

원문의 `PMS를 서버 RSA 공개키로 암호화`하는 과정은 예전 TLS 1.2 계열을 설명하기 위한 단순화다. TLS 1.3은 RSA 키 전송을 제거하고 공개키 기반 키 교환이 순방향 안전성을 갖도록 설계됐다. 참고: [TLS 1.3 표준](https://www.rfc-editor.org/info/rfc8446/)

**순방향 안전성**은 나중에 서버의 장기 개인키가 유출되어도 과거에 녹화된 통신까지 한꺼번에 복호화되지는 않는 성질이다.

## TLS 레코드

핸드셰이크가 끝나면 긴 데이터를 레코드로 나눠 전송한다.

```text
애플리케이션 데이터
→ TLS 레코드로 분할
→ 순서 정보와 함께 인증·암호화
→ TCP로 전달
```

원문은 `데이터 + HMAC`을 암호화하는 예전 구조를 설명한다. TLS 1.3에서는 일반적으로 AES-GCM 같은 AEAD 알고리즘이 암호화와 무결성 검사를 함께 수행한다.

# 8.7 IPsec과 VPN

TLS가 애플리케이션 데이터를 보호한다면 IPsec은 IP 패킷 자체를 네트워크 계층에서 보호한다.

## VPN

물리적인 전용선을 설치하는 대신 공공 인터넷 안에 암호화된 가상 통로를 만드는 것이 VPN이다.

```text
회사 A 내부 패킷
→ VPN 게이트웨이가 통째로 포장·암호화
→ 공공 인터넷 통과
→ 회사 B 게이트웨이가 복호화
→ 원래 목적지로 전달
```

바깥 라우터는 외부 IP 헤더를 보고 전달할 수 있지만 안쪽의 원래 패킷 내용은 볼 수 없다.

## AH와 ESP

- **AH**: 출발지 인증과 무결성 제공, 기밀성 없음
- **ESP**: 기밀성, 인증, 무결성, 재생 공격 방지 등을 제공할 수 있음

실제로는 ESP가 주로 사용된다. 참고: [ESP 표준 RFC 4303](https://www.rfc-editor.org/rfc/rfc4303)

## SA

SA는 `이 방향으로 패킷을 보호할 때 사용할 보안 설명서`다.

포함되는 정보:

- SPI라는 식별자
- 출발지와 목적지
- 암호화 알고리즘과 키
- 무결성 알고리즘과 키
- 순서 번호 정보

SA는 단방향이다.

```text
A → B용 SA
B → A용 SA
```

양방향 통신에는 최소 두 개가 필요하다.

## SAD와 SPD

- **SPD**: 이 패킷을 보호할 것인가? 어떤 SA를 적용할 것인가?
- **SAD**: 그 SA에서 어떤 키와 알고리즘을 사용할 것인가?

```text
SPD = 무엇을 처리할까?
SAD = 어떻게 처리할까?
```

## ESP 터널 모드

```text
[새 외부 IP 헤더]
[ESP 헤더: SPI, 순서 번호]
[암호화된 원래 IP 패킷 + 트레일러]
[무결성 검증값]
```

- SPI: 어떤 SA를 사용할지 찾는다.
- 순서 번호: 재생 공격을 방지한다.
- 암호화: 내부 패킷을 보호한다.
- 인증값: 패킷 변조 여부를 확인한다.

## IKE

SA와 키를 사람이 일일이 설정하기 어려우므로 IKE가 자동으로 합의한다.

현대 IKEv2의 대략적인 과정:

- `IKE_SA_INIT`: 알고리즘·넌스·Diffie–Hellman 값 교환
- `IKE_AUTH`: 상대 인증 및 첫 IPsec Child SA 생성

이후 필요하면 Child SA를 추가하거나 키를 교체한다. 참고: [IKEv2 표준](https://www.rfc-editor.org/info/rfc7296/)

> 원문의 `1단계·2단계` 설명은 구형 IKEv1에 가까운 설명이다.

# 8.8 Wi-Fi와 4G/5G 보안

## Wi-Fi

무선 신호는 주변에 퍼지기 때문에 누구든 프레임을 수신할 수 있다. 따라서 다음이 필요하다.

- 장치와 네트워크의 상호 인증
- 무선 구간 암호화
- 세션마다 사용할 키 생성

## Wi-Fi 보안 발전

- **WEP**: 심각하게 취약함
- **WPA**: WEP의 임시 개선
- **WPA2**: AES 기반 보호 도입
- **WPA3**: 더 발전된 인증 및 보안 기능 도입

## 기업용 Wi-Fi의 역할

```text
이동 장치 ↔ AP ↔ 인증 서버
```

- 이동 장치: 접속하려는 노트북·휴대전화
- AP: 무선 연결 중계 및 인증자 역할
- 인증 서버: 실제 사용자·장치 자격 확인

EAP 메시지는 무선 구간에서 EAPoL에 담기고, AP에서 인증 서버 방향으로는 흔히 RADIUS에 담겨 전달된다.

## 키 합의

양쪽이 이미 알고 있는 비밀 또는 인증 결과와 다음 값들을 섞어 세션키를 만든다.

- 양쪽의 넌스
- 장치와 AP의 주소
- 공유된 기본 키

두 사람이 같은 재료와 계산법을 사용하므로 세션키를 네트워크로 그대로 보내지 않고도 같은 키를 만들 수 있다.

## 4G/5G

휴대전화의 SIM과 통신사의 가입자 서버는 가입자별 비밀키를 공유한다.

```text
1. 통신사가 일회용 문제를 보낸다.
2. SIM이 비밀키로 응답을 계산한다.
3. 통신사가 예상 응답과 비교한다.
4. 서로 네트워크·가입자를 인증한다.
5. 무선 통신용 세션키를 생성한다.
```

비밀키 자체는 네트워크로 보내지 않는다.

원문은 주로 4G AKA 구조와 용어를 사용한다. 5G에서는 영구 가입자 식별자인 SUPI를 그대로 보내지 않고 공개키로 감춘 SUCI 형태로 전송할 수 있도록 개인정보 보호도 강화됐다. 참고: [3GPP의 5G 인증 설명](https://www.3gpp.org/technologies/akma)

# 8.9 방화벽과 IDS/IPS

## 방화벽

방화벽은 학교 정문 경비원과 같다.

- 모든 출입이 정문을 지나게 한다.
- 허가된 출입만 통과시킨다.
- 경비실 자체도 공격에 안전해야 한다.

## 전통적인 패킷 필터

패킷 하나의 헤더를 보고 판단한다.

- 출발지·목적지 IP
- TCP·UDP 같은 프로토콜
- 출발지·목적지 포트
- SYN·ACK 같은 TCP 플래그
- 들어오는 방향과 나가는 방향

단점은 그 패킷이 정상 연결의 일부인지 충분히 알지 못한다는 것이다.

## 상태 기반 방화벽

현재 진행 중인 연결 상태까지 기억한다.

```text
SYN → SYN-ACK → ACK → 데이터 → FIN
```

공격자가 `ACK=1`인 가짜 패킷을 보내도 실제 연결 테이블에 없는 패킷이면 차단할 수 있다.

```text
일반 패킷 필터 = 입장권 모양만 확인
상태 기반 방화벽 = 실제 입장 기록까지 확인
```

## 애플리케이션 게이트웨이

프록시처럼 애플리케이션 내용을 이해하면서 대신 연결한다.

```text
내부 사용자 ↔ 게이트웨이 ↔ 외부 서버
```

더 정교하게 인증하고 내용을 검사할 수 있지만 다음 단점이 있다.

- 애플리케이션별 지원이 필요하다.
- 모든 데이터가 중계되어 성능 비용이 발생한다.
- 게이트웨이가 내용을 알 수 있으므로 신뢰해야 한다.

원문의 SSL은 현재 용어로는 **TLS**라고 부르는 것이 적절하다.

## IDS와 IPS

- **IDS**: 수상한 행동을 발견하고 경고한다.
- **IPS**: 수상한 행동을 발견하고 직접 차단한다.

```text
방화벽 = 출입 규칙을 검사하는 경비원
IDS = CCTV를 보고 신고하는 관제실
IPS = CCTV를 보고 즉시 문까지 잠그는 관제실
```

# 전체 흐름 압축 정리

```text
누구야?
→ 인증·인증서·넌스

내용을 숨길까?
→ 암호화

내용이 바뀌었나?
→ 해시·MAC·전자서명

키를 어떻게 나눌까?
→ 공개키·Diffie–Hellman·세션키

어느 계층을 보호할까?
→ 이메일 / TLS / IPsec / Wi-Fi·이동통신

조직 전체를 어떻게 지킬까?
→ 방화벽 / IDS / IPS
```

## 반드시 기억할 네 문장

1. **암호화**는 내용을 숨기고, **해시**는 메시지의 지문을 만든다.
2. 해시만으로는 공격자의 위조를 막지 못하므로 **MAC이나 전자서명**이 필요하다.
3. 수신자의 **공개키로 암호화**하면 대응하는 수신자의 **개인키로 복호화**한다.
4. **전자서명은 개인키로 만들고 공개키로 검증**한다.
