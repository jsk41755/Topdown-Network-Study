<summary>공개키 방식과 비밀키 방식은 실제로 어떻게 쓰이는가?</summary>

현실의 보안 프로토콜은 공개키 방식과 비밀키 방식을 하나만 선택해서 쓰지 않고, 두 방식을 함께 사용한다. 공개키 방식은 키를 안전하게 공유하는 데 유리하지만 느리고, 비밀키 방식은 이미 공유된 키가 있을 때 데이터를 빠르게 암호화하는 데 유리하기 때문이다.

```text
공개키 방식으로 세션 키를 안전하게 만들고
→ 대칭키 방식으로 데이터를 빠르게 암호화하고
→ MAC(HMAC) 또는 인증 태그로 변조 여부를 검증한다
```

즉, 공개키 방식은 주로 **안전한 키 교환 또는 인증**에 사용되고, 비밀키 방식은 실제 데이터 전송 과정에서 **빠른 암호화**에 사용된다. 이후 MAC(HMAC)이나 인증 태그를 이용해 데이터가 중간에서 변조되지 않았는지도 확인한다.

<details>
<summary>왜 CA에 인증받은 인증서는 믿을만한가?</summary>

CA가 발급했다고 해서 인증서가 **본질적으로 안전한 것은 아닙니다.** 브라우저와 운영체제가 특정 CA를 신뢰하도록 미리 등록해 두었고, 그 CA가 정해진 검증 절차를 따른다고 전제하기 때문에 믿는 것입니다.

핵심은 **신뢰 체인(Chain of Trust)** 입니다.

1. 브라우저나 운영체제에는 신뢰할 수 있는 **루트 CA 인증서** 목록이 내장되어 있습니다.
2. 웹사이트 인증서는 보통 중간 CA가 발급합니다.
3. 중간 CA 인증서는 다시 루트 CA의 개인키로 서명되어 있습니다.
4. 브라우저는 각 서명을 루트까지 순서대로 검증합니다.
5. 최종적으로 신뢰 저장소에 있는 루트 CA까지 연결되면 인증서를 신뢰합니다.

예를 들면 다음 구조입니다.

```text
신뢰된 루트 CA
↓ 서명
중간 CA 인증서
↓ 서명
example.com 인증서
```

### 인증서가 없는 경우

```text
사용자 → 서버 공개키 요청
공격자 → 자신의 공개키를 서버 것처럼 전달
사용자 → 공격자의 공개키로 암호화
```

암호화는 정상적으로 이루어지지만, 공격자가 중간에서 내용을 읽을 수 있습니다. 이것이 **중간자 공격(MITM)** 입니다.

### 인증서가 있는 경우

```text
서버: 공개키 + CA가 서명한 인증서 전달
브라우저: CA 서명과 도메인 확인
브라우저: 검증된 공개키를 이용해 보안 연결 수립
```

따라서 인증서는 암호화를 수행하는 도구라기보다는, **암호화에 사용할 공개키의 신원을 보증하는 도구**입니다.

</details>
